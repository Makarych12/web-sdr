# Переработка управления приёмником — 2026-10-15

## Аудит и изменения

Исходное состояние: 66 unit-тестов проходили. Частота React хранилась дробным числом кГц; шаг по умолчанию 1 кГц, ввод принимал только Number. Отдельные VfoDial/FineTune дублировали настройку. SpectrumRenderer.setView и tune/changeView очищали историю. AudioWorklet уже существовал, как и прямой WSS, generation guards, heartbeat и reconnect с backoff. Эти механизмы сохранены.

- `src/tuning.ts`, `FrequencyDigits.tsx`, `main.tsx`, `StepControl.tsx`: основное сохраняемое состояние — целое `frequencyHz`. Десятичный ввод разбирается по разрядам без округления до кГц; субгерцевый ввод отклоняется. Существующие компоненты диапазонов/избранного и waterfall используют адаптер кГц. В строке команды Kiwi ровно три знака после точки кГц, сформированные из целых герц. Добавлены все девять шагов, режимные значения, Enter, стрелки/PageUp/PageDown и колесо над разрядами.
- `radio.ts`, `main.tsx`, `useSpectrumGesture.ts`: независимые RF-границы, Narrow/Normal/Wide; USB 300…2700, LSB −2700…−300, wide ±100…3000; CW ±250/500. Границы и вся полоса перетаскиваются; фон панорамируется, центральный маркер настраивает. Касание настраивает, двойной клик центрирует, колесо масштабирует вокруг курсора, Shift+колесо настраивает. «К частоте» возвращает VFO в центр.
- `shared/kiwiProtocol.js`: ручной AGC gain; для CW преобразование RF-фильтра в аудиополосу Kiwi с тоном 600 Гц. Гетеродин сдвигается на −600 Гц, обе границы на +600 Гц: абсолютная полоса и выбранная RF-несущая сохраняются. На границе диапазона сдвиг ограничивается. Поэтому сырое `freq` CW отличается от RF-частоты на BFO; это необходимое преобразование, а не потеря точности. Проверено по [исходникам Kiwi](https://github.com/jks-prv/Beagle_SDR_GPS/blob/master/web/openwebrx/openwebrx.js), функции freq_dsp_to_car / freq_car_to_dsp.
- `spectrumRenderer.ts`: ограниченная история 480 строк с частотными координатами каждой строки, проекция при pan/zoom, canvas работает через rAF. Данные вне накопленного обзора остаются пустыми. Переключение сервера очищает историю.
- `public/audio-worklet.js`: старт 200 → 120 мс; порог сброса старого звука 750 → 450 мс, сохранение последних 180 мс или адаптивной цели. При underrun цель растёт до 300 мс, после 60 секунд стабильного вывода снижается; переходы сглаживаются. Очередь измеряется по реальному числу PCM-сэмплов, `?debug` показывает queue/target/underrun. Это вклад очереди, не end-to-end задержка.
- `transport.ts`, `ReceiverPicker.tsx`, `server/gateway.js`: HTTPS предпочитается шлюзу, реальная ошибка direct WSS разрешает повтор того же сервера через gateway. Каталог сортирует direct выше gateway, сохраняет избранное. Проверка выбранного узла `/status` ограничена четырьмя запросами, timeout 5 с, cache 60 с. HTTP responseMs измеряется от шлюза и не выдаётся за browser RTT. Аудио/WF считаются доступными только при поступлении обоих потоков.
- `main.tsx`, `features.css`: единая панель; сохранение частоты, режима, фильтра, шага, gain/AGC, zoom/центра и громкости, без автозвука. QSL, избранное, быстрые диапазоны, поиск позывного и PWA сохранены. `public/sw.js` обновляет cache.

`npm test`: 73/73. `npm run build`: успешно. Полезные новые проверки: десятичный ввод/1 Гц, все шаги, пресеты, persistence, direct transport, абсолютная CW-полоса, адаптация PCM. Существующие тесты проверяют coalescing/flush, reconnect и устаревшие события.

## Фактическая проверка production

Production `https://web-sdr.vercel.app` доступен публично; `/api/health` подтверждает commit деплоя. На Vercel прошли control/gesture/PWA-тесты; gateway VK5ARG передал реальные PCM/WF во всех пяти режимах. В статусном API устранён обнаруженный production 404 добавлением rewrite в `vercel.json`.

15 минут прямого приёма Niendorf: 2026-10-15 08:13:51–08:28:51 UTC, 91 снимок раз в 10 секунд. На каждом снимке «В эфире», один AudioContext, два прямых SND/WF-сокета, история до 480 строк. Очередь PCM по ненулевым снимкам: 121.8–417.7 мс, средняя 283.4 мс. Это измерение клиентской очереди, не задержки интернета/приёмника/динамика.

**Критерий «без единого пропуска аудио» не пройден:** 53 231 выходной сэмпл underrun, приблизительно 1.11 с суммарно при 48 кГц за 15 минут. Связь не обрывалась, но пропуски буфера были; точную долю сети и нагрузки клиентской машины этот тест не разделяет. Нельзя объявлять непрерывный звук без потерь или полностью закрывать критерии готовности.

После принудительного закрытия SND восстановлены 7074.250 kHz / USB / 300…2700 / zoom 6 / AGC slow, AudioContext остался один. В этом первом production-деплое reconnect использовал gateway (один клиентский сокет), поэтому затем политика исправлена: перед fallback делается повтор direct на том же сервере. Результат повторной проверки финального деплоя записывается ниже. В локальном 15-минутном запуске reconnect сохранил два прямых сокета и один AudioContext; ошибок JavaScript не было.

Для сравнения отдельно запущен исходный frontend из родительского commit `ab8f6e1`: 120 секунд, стартовая цель 200 мс, фактическая очередь по 12 ненулевым снимкам примерно 214–492 мс, средняя 425 мс; тоже были underrun. Условия и длительность запусков различаются, это наблюдения, а не контролируемый end-to-end benchmark.

Дополнительно: обычный Chromium 390×844 — 59.8 rAF FPS, максимальный интервал 33.3 мс в 5-секундном замере после оптимизации. Синтетическое 4× CPU slowdown ранее давало 11–17 FPS: заявлять 30–60 FPS на любом слабом телефоне нельзя. Сохранённая история теперь рисуется группами строк с одинаковым диапазоном, убрана дорогая тень спектральной линии. Искусственная блокировка UI на 250 мс вызвала временный underrun, затем очередь восстановилась без смены подключения.

Мобильные размеры 360×800, 390×844, 844×390 проверены в Chromium; исправлены наложение поиска позывного и сжатая шкала S-meter. Проверены горизонтальный/вертикальный pinch, RF-якорь колеса (с допуском одного физического пикселя), tap, фон-pan и VFO-drag. Физический Chrome Android, системная установка PWA и аппаратная аудиозадержка не проверялись.

Артефакты запусков сохраняются в ignored `artifacts/`; воспроизведение: `npm run verify:controls`, `verify:gestures`, `verify:pwa`, `verify:session` (по умолчанию 900 секунд), `verify:performance`. Для production установить `TEST_APP_URL=https://web-sdr.vercel.app`, для session также `TEST_REPORT=artifacts/receiver-production-15min.json`.
