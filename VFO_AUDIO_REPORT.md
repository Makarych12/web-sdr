# Непрерывный звук при настройке VFO — 2026-10-11

## Точная причина и воспроизведение до исправления

Регрессия находилась в `src/main.tsx`, функции `tune()`: `if (audioChanged) player.current?.port.postMessage({ reset: true })`. `audioChanged` становился true при каждом изменении частоты. Это было добавлено в предыдущем исправлении `e3b2246`.

Обработчик reset в `public/audio-worklet.js` удаляет queue, сбрасывает buffered/pos/started и устанавливает startup target 200 мс. При VFO-событиях чаще одного раза в 200 мс звук не успевает начать играть снова. Входящие реальные PCM при этом продолжают приходить.

Проблема **воспроизведена до изменения кода** на реальном Niendorf KiwiSDR: 20,035 с колеса VFO, 391 событие настройки, 468 входящих PCM-пакетов, 391 reset аудиоочереди. Ненулевой звук — только 1/185 замеров; playedFrames вырос всего на 11 264 при AudioContext 48 kHz. После остановки звук вернулся. Context оставался running, gain = 0,7, количество AudioContext/AudioWorklet/WebSocket и авторизаций во время настройки не менялось. Артефакт: `artifacts/vfo-audio-before.json`.

## Минимальное исправление

В `src/main.tsx` удалены только `audioChanged` и отправка PCM reset из обычного `tune()`. Настройка частоты, режима и фильтра теперь сохраняет текущую аудиоочередь. Работающий звук не ждёт отпускания ручки.

Другие исходники приложения, дизайн, мобильная вёрстка, renderer, серверы и аудиобуфер не изменялись. Сохранены:

- синхронное обновление отображаемой частоты и маркеров;
- один pending tune, throttle 40 мс и чтение самых последних настроек перед отправкой;
- немедленный flushTune на pointerup/pointercancel/lostpointercapture;
- существующий короткий jitter buffer и ограничение PCM-очереди;
- сброс аудио при реальной смене соединения/сервера.

Проверен путь pointerdown/move/up, wheel, клавиатуры и шаговых кнопок. Он не вызывает stop/pause/mute/reconnect, не меняет gain и не создаёт новый AudioContext/AudioWorklet/WebSocket. Audio-компонента с key={frequency} нет; создание и cleanup сеанса не зависят от frequency. Приём PCM не блокируется dragging/tuning-флагами. KiwiProtocol.apply отправляет SET mod/freq по существующему SND-каналу, без повторной авторизации. Основное рисование spectrum/waterfall идёт через requestAnimationFrame; инструментальная проверка не нашла drawImage/putImageData из VFO-событий.

## Реальная проверка после исправления

Использована исправленная локальная production-сборка и настоящий HTTPS/WSS Niendorf KiwiSDR. Chromium воспроизводит мышь, колесо и touchscreen через CDP. Это браузерная эмуляция пальца, а не физический телефон. Исправление пока не опубликовано.

`node tests/vfo-audio-browser.mjs`: **45 проверок**. В каждом режиме AM/USB/LSB/CW/FM — 20 с удержания и вращения мышью, 20 с колеса, 20 с drag пальцем, с частыми сменами направления. Затем проверены кнопки вверх/вниз при шагах 1/10/100/1000/5000/10000 Hz. Шаги также менялись внутри длинных прогонов.

Всего: **301,085 с активной настройки**, 5431 событие VFO, **2794/2794 замеров с ненулевым реальным звуком**. Reset во время настройки — 0; прирост underflowFrames — 0. На всех этапах работал один AudioContext, один AudioWorklet и один Kiwi-сеанс: один SND WebSocket для аудио и команд + один W/F WebSocket для панорамы. Ни новых соединений, ни повторной авторизации во время настройки не было. Gain сохранялся; context оставался running. Waterfall sequence продолжал расти, последнее SET mod/freq точно совпадало с показанной частотой.

Время очереди выше рассчитано из телеметрии buffered при входной частоте около 12 kHz. Это измерение запаса воспроизведения, а не полной задержки RF → физический динамик. Накопления многосекундного запаздывания нет.

`TEST_TERMINATION_ONLY=1 node tests/vfo-audio-browser.mjs`: pointerup, pointercancel и lostpointercapture отправляют последнюю pending частоту за **0,2–0,3 мс**. После них отложенных tune-команд нет, очередь не сбрасывается. Дополнительно подтверждены ненулевой аудиовыход, реальные цветные trace-пиксели spectrum и строки waterfall.

`npm run verify:latency`: 40 проверок прошли; VFO → отправка tune до **72.9 мс**, VFO → UI до **3.2 мс**, release → финальный tune **0,3 мс**. Проверены также прежний gateway, stop/restart, смена Kiwi и отсутствие дублей.

`npm test`: **40/40**. `npm run build`: успешно. Ошибок страницы в длительном и event-тестах нет.
